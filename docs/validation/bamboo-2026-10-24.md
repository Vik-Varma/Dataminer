# Bamboo collision and offset, measured on BDS 1.26.52.3

Written 2026-10-24. The evidence behind `out/1.26.52/bamboo.json`. The author is on the **dirty side**
for bamboo shapes: the offset model's form came from static and dynamic analysis of BDS. This note
gives facts and method only.

## Setup

- Linux BDS 1.26.52.3 from minecraft.net, `bedrock_server` SHA-256
  `0a490c711d4a2ce075debcd979e8862b7eaba008373f9970f0edbb67f98f9207`, run on Ubuntu 24.04 (container,
  kernel 6.18, x86-64).
- `server.properties` changes from the shipped file: `server-authoritative-movement-strict=true`,
  `player-position-acceptance-threshold=0.0001`, `online-mode=false`, `allow-list=false`,
  `transport=raknet`, `allow-cheats=true`, `default-player-permission-level=operator`,
  `gamemode=creative` (the test player was switched to survival), `difficulty=peaceful`,
  `view-distance=8`, `player-idle-timeout=0`, `enable-lan-visibility=false`.
  Game rules: `randomtickspeed 0`, `dodaylightcycle false`, `doweathercycle false`, `domobspawning false`.
- The container has no IPv6. BDS refuses to start if its IPv6 socket fails, so an `LD_PRELOAD` shim
  turned its `AF_INET6` socket into an IPv4 one. Gameplay used the IPv4 port only.
- The client was a headless Go program using gophertunnel v1.62.0 (MIT, protocol 2193). It sends
  `PlayerAuthInput` at 20 Hz. **BDS 1.26.52 does not simulate the player until the client sends
  `ServerBoundLoadingScreen` with type end**; before that it neither moves the player nor corrects it.
- Blocks were placed and the player teleported from the server console (`setblock`, `tp`).

## Method

A strict server corrects any claimed position more than 0.0001 off its own simulation. The client
claims its last known position; the server's `CorrectPlayerMovePrediction` packets (at most about
one every 6 ticks) give the server's position. A run walks the player into the block for 30 ticks
with forward input at yaw −90 (+x), 90 (−x), 0 (+z) or 180 (−z), releases input, and is accepted only
if no correction arrives in the last 10 ticks. The stop is then the server's position.

- **Player half-width:** walking into a full stone block from all four sides stops the player
  exactly 0.3 from each face (four runs).
- **Faces:** stop + 0.3 (approaching from −) or stop − 0.3 (from +) is the stalk's face.
- **Top:** dropping the player from 2.5 blocks above onto the stalk's centre lands its feet at
  block y + 1.00002 for all 12 states (28 drops).

## Results

| What | Value | Method |
| --- | --- | --- |
| Thin stalk box (all 3 leaf sizes, both `age_bit`) | x, z 8–10 /16; y 0–16 /16 | measured (y min: read from our running BDS) |
| Thick stalk box (all 3 leaf sizes, both `age_bit`) | x, z 8–11 /16; y 0–16 /16 | measured (y min: read from our running BDS) |
| Offset, x and z | −0.25 + k/30, k ∈ 0..15 (16 steps) | measured; model below |
| Offset, y | none | measured (drops), and range 0 read from our running BDS |
| Offset inputs | block x and z only; not y | measured (y = 200 and y = 210 agree with one model) |
| Offset applies to collision | yes | measured |
| Offset applies to the outline | yes | inferred (static analysis only) |
| Offset applies to rendering | not established | unknown (BDS has no renderer) |

The full definition of the offset (the seed from x and z, the generator, how a draw becomes a step)
is in the spec's `payload.offset.definition`, as mathematics. It was found by analysis of BDS and is
accepted only because it predicts every stop: **288 stops (260 walks, 28 drops) at 46 block columns
in all four x/z sign quadrants, from (−4095, −4097) to (3000, 2999), at y = 200 and y = 210. Worst
error 0.00049 block** (float32 resolution at |x| ≈ 4000; at most 0.00002 block within 100 blocks of the origin).
`dataminer measure bamboo` refuses to write the spec if any stop is off by more than 0.001.
